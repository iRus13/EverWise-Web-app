# Continued iOS and web quality work

This continues the full-app request after audit head `68a4bbe`. The original
live-account, provider, App Store/TestFlight and physical-device acceptance gaps
remain open. The overall goal is not complete.

## Repairs in this change

- Exercise data and learning players are loaded when an activity opens. A
  generated small catalog retains course order, badge names, completion content
  and progress requirements. A contract test rejects a stale catalog after
  curriculum edits. Authored lessons remain the only editable source of truth.
- A failed or stalled download offers retry, reload and return to the path.
  Timed-out, superseded and unmounted requests cannot replace the current screen
  or complete a lesson. Existing subscription checks still decide access before
  rendering learning content.
- Logos follow the configured build base. The install manifest and standalone
  privacy/terms return links work at both `/` and `/EverWise/`. Removed the Pages
  workflow's post-build string replacement; the build now produces correct paths.
- Added production browser checks to the PR workflow, covering both hosting
  paths, public login validation, all three deferred player types, image and
  manifest loading, and startup size limits.

## Performance evidence

The same local production build changed initial JavaScript from **1,907.14 KB**
to **1,022.58 KB**, about **46% less** before compression. Vite reports initial
gzip size changing from **514.01 KB** to **299.07 KB**, about **42% less**.
The exercise module is a separate 956.14 KB chunk (232.47 KB gzip). It is not
requested on the welcome screen. Some small metadata is present in both chunks;
this change reduces startup transfer, not total bytes after opening lessons.

Production WebKit checks at 390px and 1440px verify both hosting bases. The
script independently calculates gzip sizes using Node's default compression,
which differs slightly from Vite's compression settings. No real-network speed
or physical-device launch-time claim is made.

## Email-account recovery follow-up

The login screen now offers password reset without requiring an existing session.
It validates a real email address and rejects reserved username-only aliases,
normalizes the submitted address, and gives identical confirmation for existing
and unknown accounts. Network errors and throttling remain visible. Duplicate
submissions are suppressed, a 20-second timeout explicitly says an email may
still arrive, and leaving the screen ignores a late response. Entering recovery
clears the login password, preserves the identifier and focuses the new heading.

All 1,686 UI tests pass, including actual App wiring to a simulated Firebase reset
request. Four provider-contract tests pass. Production browser checks reject an
undeliverable alias without sending any email, at 390px and 1440px under both
hosting bases. The recovery screen is included in the expanded responsive matrix:
96 WebKit combinations pass. No real email delivery or identity recovery was
performed. Native web assets were refreshed and the simulator build/install/launch
passed again.

The performance/path commit `6e2d468` passed the entire GitHub QA run
[35487036496](https://github.com/iRus13/EverWise-Web-app/actions/runs/35487036496):
441 unit/backend/browser tests, 1,680 UI tests, production build, WebKit layouts
and both production hosting bases. The additional recovery changes trigger a
new complete CI run; that result is recorded in the PR. Startup JavaScript with
the recovery UI is 1,025.68 KB before compression, retaining the approximately
46% startup reduction.

The expanded Chromium core-screen matrix also passes on isolated recheck. A prior
local run failed only while waiting for Chrome cleanup, not a layout assertion.
The final CI run remains the complete-checkout acceptance for this revision.
