# EverWise web audit — 2026-09-11

Scope: live https://www.everwise.tips and local repairs based on GitHub main c7e7c1fcadf2b0237f71399e1774d946f884aa90. Browser: Codex in-app Chromium. User explicitly restricted testing to the signed-out experience. No production account, purchase, or service configuration was changed.

## Browser coverage

80 screen/size measurements: live welcome page (8), local questionnaire steps 1–8 (64), and local login (8). Target CSS sizes: 320×568, 375×667, 390×844, 667×375, 768×1024, 1024×768, 1440×900, 1920×1080. Browser zoom compensation produced up to one CSS pixel of rounding (320×567, 767×1024, 1024×767). Measurements checked document horizontal overflow and questionnaire controls outside horizontal bounds. None found. These are responsive emulations in one browser, not physical-device or Safari/Firefox tests.

Small-phone validation feedback and primary action were visually inspected. Long accessibility-question content can be scrolled to its final answer and submitted. Desktop pages scroll naturally; a footer below the initial viewport is not considered clipped when reachable by page scroll. Live welcome images loaded without broken images. No local console errors or warnings were reported during the final inspection.

Interactions: empty name and login validation, age input filtering, required account-step validation without account creation, radio arrows, step-heading focus after navigation, optional skipping, checkbox exclusivity, questionnaire-to-login Back navigation, and refresh. Earlier live test completed the public questionnaire to its final signup step, using synthetic answers.

## Reproduced and repaired locally

1. Validation feedback could be below the scroll viewport on small phones. Reproduction: open onboarding at 320×568 and press Start with empty fields. The live page exposes an error to accessibility but does not show it next to the action. Repair: place error feedback in the footer above the primary button.
2. Validation errors remained after editing inputs. Repair: clear local questionnaire errors when answers change and clear login errors when either credential field changes. Submission still validates again.
3. Questionnaire answers were lost during the login detour. Reproduction: reach step 8, choose Log in, press Back, then Get Started. Live app restarts empty at step 1. Repair: carry an in-memory draft to login and return to step 8, preserving prior answers. Password is excluded; draft is cleared on authentication or explicitly leaving onboarding.

## Automated verification

436 unit tests and 269 UI/component tests passed, including five new regression tests. Tests used NODE_OPTIONS=--no-experimental-webstorage to avoid Node 26 web-storage incompatibility in the existing test harness. Production build passed. Existing bundle-size warning remains. Automated mocked tests are not production service verification.

## Remaining work

- Refresh at signup returns to welcome and loses the questionnaire. Decide between a clear unsaved-work warning and an opt-in draft mechanism; questionnaire includes potentially sensitive answers, so do not indiscriminately persist it or passwords.
- Login has no visible forgot-password route. Username-only identity requires a verified recovery design before adding a misleading reset action.
- Step 7 heading is too long on small phones; shorten visible copy while retaining clear labels and narration.
- First useful learning activity requires an account after an eight-step interview. Consider a genuinely usable sample lesson.
- External service readiness: the earlier live health check reported missing billing, scam checker, narration-provider and partner configuration. Browser speech fallback can still enter a speaking state; this does not verify hosted narration or audible output.
- Full authenticated curriculum, saved-progress persistence, cross-device sync, payment/restore/cancel, account deletion, partner administration, and production error recovery remain untested in the browser under the signed-out restriction.
- Physical phones, mobile keyboards, VoiceOver, Safari/Firefox, and 200%/400% zoom need separate passes. No claim of universal accessibility or a perfect app is made.

## Delivery state

Repairs are prepared for GitHub delivery under the user’s explicit automatic-push authorization. The associated pull request records merge status. Sites publication is a separate operation from merging into GitHub; this audit did not publish the live site.


## Paywall follow-up

See [paywall research and design brief](2026-09-11-paywall-research.md) for ten research sources, rationale, product hypotheses, and remaining billing checks. The web paywall now keeps readable terms on short screens, shows the selected renewal terms beside checkout, exposes a text free exit, and describes learning access rather than an unverified checker service. Prices and server offer verification are unchanged.

The actual Paywall component passed additional automated browser measurements at all eight listed sizes, including 320×568 and 667×375. These check card/action bounds, at least 44px button height, and at least 16px financial disclosure text. A deliberately broken wide-card fixture still fails the geometry assertion, validating the detector. The final layout was also visually inspected in the in-app browser on desktop and at 320 CSS pixels; monthly/annual selection and scrolling to the CTA, free exit, and legal buttons were checked. The isolated preview uses inert checkout callbacks and does not make a purchase. UI regression tests verify the free-exit callback and selected-plan accessible description. Local preview does not establish production billing readiness.
